# 02 · 数据模型与数据库选型

> 本文记录数据库选型变更（SQLite → PostgreSQL）、现有数据模型的问题，以及**数据模型重设计方向**。
> 属于方向性蓝图；具体 schema 与迁移脚本待后续里程碑实现。

## 1. 现状（上一阶段）

- 数据库：**SQLite**（`@libsql/client` 驱动）+ **Drizzle ORM**，本地文件 `.data/my-resume.db`。
- 定位：轻量化、易上手、单机可跑（适合早期与个人项目）。
- 简历只有**一份**：`resume_drafts` 通过固定 `resume_key` 做**单槽位** upsert，整份简历以 `resume_json`（JSON 列）存储。

### 字段级 locale 的现状

简历领域模型 `StandardResume`（`apps/server/src/modules/resume/domain/standard-resume.ts`）里，**每个可翻译文本字段都包一层 locale**：

```ts
export interface LocalizedText {
  zh: string
  en: string
}
// profile.fullName: LocalizedText、experiences[].role: LocalizedText、skills[].keywords: LocalizedText[] …
```

> 完整字段结构见 `standard-resume.ts`（`meta / profile / education / experiences / projects / skills / highlights`）。

## 2. 痛点

1. **字段级 `locale` 包裹不合理**：为了国际化，把每个字段包成 `{ zh, en }`，导致数据结构与读写都被这层包裹污染。
2. **简历只能存一份**：单槽位设计无法承载“多语言/多定制版本并存”。
3. **SQLite 局限**：不适合后续 AI/向量能力与更复杂的数据关系。

## 3. 目标：切换到 PostgreSQL

- 选用 **PostgreSQL**，原因：
  - 便于后续加入 **pgvector**，支撑 AI 与向量相关功能。
  - 字段设计可以重新做得更合理（不再迁就 SQLite）。
- 这是新项目重构，**数据模型重新设计**，不沿用旧结构直接搬。

## 4. 数据模型重设计方向

### 4.1 去掉字段级 locale 包裹

- 不再用 `LocalizedText { zh, en }` 包裹每个字段。
- 语言差异改由**“多份 draft”**在**数据行层面**承载（见下）。

### 4.2 简历支持多份（≤ 20 份）

- 简历可以有**多份**，上限暂定 **20 份**。
- 每份是一份独立的 **draft（草稿/版本）**。

### 4.3 用多份 draft 承载“多语言 + 定制”

- **同一字段**在不同 draft 里各自编辑，互不干扰（不会像字段级 locale 那样混在一起）。
- 实际使用时，**选用对应的 draft 版本**即可：
  - 随时**切换**展示的简历；
  - 随时**部署/发布**对应版本；
  - 可对文本做**本地化定制**（不同语言/面向不同场景的定制稿）。

> 心智模型：**“一份简历 = 一个 draft”**，语言与定制都是 draft 的属性，而非字段的属性。

## 5. 字段设计（方向）

- 沿用领域模型 `StandardResume` 的结构（profile / education / experiences / projects / skills / highlights）作为**内容形状**参考。
- 但**去掉其中的 `LocalizedText` 包裹**，字段回到**单语言字符串/数组**；
  语言维度上移到 draft 层（每份 draft 声明自己的 locale / 用途）。
- 主键与关系、快照与发布的表结构，随 PostgreSQL 落地时重新设计（**待定**）。
