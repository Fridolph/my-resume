# 01 · 重构蓝图与三端职责

> 本文记录本次重构的**动机、目标与原则**，以及 `rs-web` / `rs-admin` / `rs-api` 三端的**定位与边界**。
> 属于蓝图级约定；具体实现随里程碑渐进落地。

## 1. 背景与动机

- 旧后台结构/分层没做好，功能越加越多，**越写越臃肿**，可读性与可维护性下降。
- 这是**新项目级别的重构**：准备自己重新写一遍，而不是在旧代码上打补丁。
- 希望在**写好基础设施与公共部分**的前提下推进，避免后续“到处拼凑代码、量大难维护”。

## 2. 目标与原则

- **有规划、有目的、按部就班、稳扎稳打、有序推进**。
- 代码保持**最佳实践**：可读、可维护。
- 采用**教学式渐进重构**：一边开发一边学习，不一次性铺满。
- 先把**路由、布局、组件、utils、libs、plugins、hooks**等基础设施与公共部分做好，再往上堆业务。

## 3. 三端定位与边界

### 3.1 rs-web —— 纯展示端

- **只做展示**：简历公开展示（已具备**语言版本切换**、**主题切换**）。
- **外加 AI 对话功能**（与访客交互）。
- **保持纯粹**：不做概览等其它冗余功能（旧 web 曾加过概览，此处不再纳入）。

### 3.2 rs-admin —— 业务聚集点

- 是**所有业务功能的聚集点**。
- **可对 `rs-web` 进行定制展示**：如布局、切换方式、顺序改动等。
- 承载（或触发）多类 **AI 集成功能**（见 [03-AI-能力与迁移清理计划](./03-AI-能力与迁移清理计划.md)）。

### 3.3 rs-api —— 功能与逻辑承载体

- 主要承载三端所需的**功能与逻辑**。
- 现状对应 `apps/server`（即“api”）。
- **后续将完全重构**。

## 4. 基础设施先行（分层）

先立骨架、再填业务。`rs-admin` 已确立如下分层约定（硬约定，详见 `apps/rs-admin/README.md`）：

```
app/       路由编排（route / layout / page）
config/    配置驱动（导航、常量、env）
types/     全局类型
utils/     纯函数工具
shared/    跨域共享（components / hooks / lib）
features/  业务域（自治单元，禁跨域互引）
```

依赖方向单向：`app → features → shared → utils / config / types`。
数据请求只允许出现在 `apis/` 与 `hooks/`；样式单一来源（antd token），禁止 `!important`。
`rs-web` / `rs-api` 的分层约定后续各自界定（**待定**）。

## 5. 非目标（本阶段明确不做）

- 不一次性把目标架构全部铺满（违反教学节奏与过程感）。
- 不在单个任务里跨多个里程碑扩张范围。
- 不在蓝图阶段写成可直接落地的完整实现方案。

## 6. 当前进度（快照）

- `rs-admin`：布局壳、两级导航、页面壳、本地 mock 已就绪。
- `rs-web` / `rs-api`：未开始。
- 数据库从 SQLite 切 PostgreSQL 的方向已定，模型重设计见文档 02。
